# Authentication setup and outstanding verification

Implementation date: 2026-10-22 (Asia/Dhaka). Automated tests NOT RUN by user instruction. Compilation evidence is recorded in the session history. Migrations, live PostgreSQL/RLS/concurrency checks and SMTP delivery NOT RUN.

1. Back up the database and review migration 000004. Apply it with the existing migration tool using privileged MIGRATION_DATABASE_URL and a separately set runtime DATABASE_URL. No historical migrations are edited. Migration 000004 is atomic and forward-only; its down file refuses rollback so credentials, sessions and security policies cannot be accidentally erased.
2. Provision the eghissab_app password independently with an administrator; migration 000003's historical example password must be replaced. Set POSTGRES_APP_PASSWORD for Compose. No real secrets or existing .env values were read or changed. Do not run the API as the migration role. Startup checks require eghissab_app, no elevated attributes/role memberships, no identity-table ownership, FORCE/ENABLE RLS and the new authentication functions. The dedicated eghissab_identity_executor role is NOLOGIN, NOBYPASSRLS, has no memberships and must never be granted to runtime users.
3. Populate backend/.env.sample's AUTH_* and SMTP_* settings in your private environment. Generate AUTH_SIGNING_KEY from at least 32 random bytes encoded in standard base64. Configure AUTH_ISSUER and AUTH_AUDIENCE consistently; changing the signing key invalidates existing access tokens. Key rollover requires coordinated configuration; no multi-key grace window is implemented. SMTP must support verified STARTTLS (TLS 1.2+); implicit TLS on port 465 is not supported. Username/password are optional only when both are empty and your relay supports unauthenticated TLS delivery. The backend refuses startup without valid mail/auth configuration. Migration commands do not require auth/mail configuration.
4. Configure AUTH_VERIFICATION_URL to an HTTPS frontend verification page (not a GET API endpoint); that page POSTs the token to /auth/verify-email. Configure only trusted reverse-proxy CIDRs for correct per-client rate limits. Restart the API after migration/configuration, not before; database health alone does not imply schema readiness. Compose forwards authentication settings to backend in both production and development; development now uses the restricted role too.
5. When authorized, verify register→email→verify→login→me→refresh→me→logout, rejected old tokens, logout-all across devices, five failed challenge attempts, expiry/resend cooldown, concurrent refresh/reuse revocation, suspended users, cancellation/rollback, cross-user RLS denial and runtime inability to read/write credential/session/challenge tables. Verify real relay delivery and proxy-address spoof resistance. None of these runtime checks has been executed here.

Migration prerequisites/risks: privileged role/schema administration is needed. Existing verified email addresses that collide after lowercasing cause the new unique index to fail atomically; reconcile those records through a separately reviewed, non-destructive process. Existing runtime/executor role memberships cause migration refusal. Existing identity contacts/users are preserved; pending duplicate email contacts are not merged. Login selects only verified email credentials; MFA/recovery/social login are outside this requested lifecycle.

Retention: keep spent refresh rows for at least the entire family's absolute expiry so replay remains detectable. Plan an administrator-owned maintenance job to delete expired session families/challenges and old auth_attempts rows after the agreed security retention period (for counters at least 24 hours); no worker/job or retention policy is silently installed. Persistent rate counters grow with distinct addresses/IPs. Synchronous SMTP is an injectable adapter, with bounded timeouts and a resend recovery path, not a durable outbox or background retry worker.

The API still contains the earlier public listing prototype with no corresponding listings migration. Identity authorization does not establish organization/store membership or make that prototype tenant-safe. Those remain separately scoped tasks.
