# ADR-006 — Identity lifecycle implementation

Status: IMPLEMENTED_UNVERIFIED technical choices; protocol scope explicitly authorized by the user on 2026-10-22. This does not invent approval of unrelated product/security policies.

Context: existing global identity/contact/credential/challenge/session schema and database/sql modular monolith; no authentication implementation or RLS policies. User explicitly requested complete registration, email proof, login, JWT access tokens, refresh rotation/reuse revocation, authenticated context, logout, additive migrations and no automated tests.

Decision: reuse the six existing identity tables; add rotated_at, family/email indexes and a persistent hashed rate-budget table. Choose bcrypt cost 12 with explicit 12–72 byte limits, 10-minute HS256 access tokens, 30-day absolute refresh families, SHA-256 hashes of 256-bit opaque refresh/verification secrets, 30-minute verification expiry/five attempts/60-second resend cooldown, and explicit bearer/JSON transport. These lifetimes and operational defaults are implementation choices, not separately approved business requirements.

Use restricted SECURITY DEFINER bootstrap functions with fixed search_path and dedicated NOLOGIN owner. FORCE RLS on identity tables, own-profile/contact reads with transaction-local app.user_id, no direct runtime credential/session/challenge DML. Runtime must use eghissab_app and pass startup role/RLS checks. Use existing TxManager with distinct scoped authorization marker and fail-closed nesting. Serialize session mutations with the user row; invalid/reuse outcomes commit security state before HTTP errors. SMTP is synchronous, injected and requires verified STARTTLS.

Alternatives: a privileged runtime connection was rejected because it defeats row isolation; setting a general anonymous RLS bypass variable would permit arbitrary identity DML; opaque access tokens would conflict with the requested JWT scope; sliding refresh expiry permits indefinite sessions; cookie transport would require a separate CSRF/storage contract. A durable encrypted mail outbox, key-ring rollover and MFA/recovery remain future scope rather than introducing new infrastructure.

Consequences: protected requests query live session state; refresh invalidates the previous access token; concurrent refresh/lost response requires re-login; SMTP outages require explicit resend and can expose eligibility through error behavior. Migration is forward-only and may fail on existing normalized verified-email collisions. No live security/SMTP/concurrency claims follow from compilation. See authentication-api.md and deployment setup for required verification.
